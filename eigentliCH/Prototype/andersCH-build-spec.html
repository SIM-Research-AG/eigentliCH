andersCH Build specification v1.0 29 August 2026

Member application — implementation requirements

Derived from the andersCH Customer Journey proposal. Target stack: HTML/JS front end with a Python backend, matching the existing prototype. Scope: the full proposal, built in the phase order given in section 10.

Requirement IDsR-nnn functional · C-nn constraint · S-nn screen · NG-nn non-goal · D-nn open decision
AuthorityC- constraints override every R-
Instructions to the implementing agent
  1. Read sections 1, 2 and 12 before writing any code. Section 2 contains vetoes that invalidate otherwise reasonable implementations. Section 12 lists decisions you must not make on your own.
  2. Survey the existing estate first (section 9). Several components already exist in some form. Report what you find and what you propose to reuse before creating new files. Do not assume a path in this document is correct — verify it.
  3. Where a requirement is underspecified, stop and ask. Do not invent policy. Inventing a number, a rate, an assessment threshold or a regulatory position is a defect, not a gap-fill.
  4. Every requirement has an ID. Reference the ID in commit messages and in code comments where a non-obvious constraint drove the implementation.
  5. Build the acceptance checks in section 11 as executable tests, not as a manual list.

01 Scope and non-goals

andersCH is a member application with two journeys that meet in a Market Place.

SurfacePurposeCadence it must support
Planner & Life EventsBuild and maintain a plan; handle transitions. Destination is a self-determined lifeEpisodic and deep — weeks or months between sessions. No daily engagement mechanics
Knowledge & CommunityLearn how money, pensions and the economy work, up to the point of being able to offer that to othersWeekly or daily, light
Market PlaceShared third surface both journeys open onto. Supply comes partly from members who complete the ladderOccasional, transactional

Non-goals

IDNot builtWhy it matters to the build
NG-01Trade execution, order routing, custodyNo broker integration, no order objects in the data model
NG-02Decumulation and drawdown modelling — living from assets, capital against annuity, AHV timingExplicitly a later scope. Do not add withdrawal-sequencing logic to any engine call
NG-03Occupational or professional education contentThe ladder teaches financial capability only. No course catalogue for trades or professions
NG-04Any federal or accredited qualificationCapability statements are andersCH's own. No claim of accreditation in code, copy, or generated certificates
NG-05Accounts for members under 25Age floor enforced at registration. No minor-consent flows
NG-06Health or medical adviceHealth appears only as a Protection role label and as Market Place supply
NG-07Native mobile applicationsResponsive web only in this phase

02 Hard constraints

These override any functional requirement. If a requirement in section 5 appears to conflict with a constraint here, the constraint wins and the conflict is a defect in this document — report it.

IDConstraintImplementation
C-01 No personalised investment recommendation anywhere. The application may educate and may illustrate with generic arithmetic. It may not select, rank or weight instruments for an identified member Any response object that ranks instruments must carry requires_curator: true and be refused by the API unless an open CuratorSession exists. Enforce server-side, not in the UI
C-02 Illustrative arithmetic must be labelled and its assumptions stored, not hardcoded Rates, horizons and inflation live in a versioned AssumptionSet record. Every illustration response returns the assumption_set_id used. No literal rate in application code
C-03 Engines run server-side only, in the permitted runtime No engine logic, weights or model files reachable from the browser. No engine invocation from client JavaScript. All engine calls go through the Python backend
C-04 Every stored field carries a data class (the existing K0–K3 scheme). The most sensitive class never leaves the server and never appears in logs Classification is a column on the model, not a convention. A logging filter drops the top class by field name. A test asserts no top-class field appears in any log line
C-05 andersCH is sole data controller from the first intake question. No third-party analytics, tag managers, fonts-with-logging, or session recorders on any page that touches member data No external network calls from authenticated pages. Self-host fonts. A test asserts the authenticated bundle makes no cross-origin request
C-06 No notification without a prepared decision. An action item exists only if it carries the options and their consequences ActionItem.prepared_options is non-nullable with minimum length 2. An item with an empty array cannot be persisted
C-07 No gamification primitives, enforced by absence The schema contains no points, score, streak, badge, level-number, leaderboard or daily-goal field. A test greps the model layer for those identifiers and fails on a match
C-08 Market Place ordering cannot be bought The listing query accepts no paid-placement, boost, sponsor or priority parameter. Ordering inputs are limited to role match, capability evidence, and community presence. Fee fields may exist for billing but must not be readable by the ranking function
C-09 Every material change to a member's plan produces a Decision Record Writes to positions, goals and plan parameters are wrapped in a transaction that also writes a Decision. A plan mutation without a linked decision is a constraint violation, not a warning
C-10 Curator interactions are attributable Every CuratorSession records the identified curator, the entry point it was opened from, and the outcome. Immutable append-only audit table

Two doors and a shared third surface. The Know is reachable from everywhere, not from a tab.

Action items surface inside The Know, never as a badge on navigation
IDRequirement
R-001The role grid is the default authenticated landing screen, not a dashboard of widgets and not the vault
R-002The Know is a persistent panel or overlay available from every authenticated screen, carrying a Curator button at all times
R-003Action items appear inside The Know as items with prepared decisions. They must not appear as counts, dots or badges on navigation elements

04 Data model

Entities and their essential fields. Field lists are the minimum, not the maximum. data_class uses the existing K0–K3 scheme — confirm the exact values against the estate before implementing.

// core member and plan
Member {
  id, created_at, age_at_registration // >= 25, see NG-05
  display_name, locale, stage_hint            // stage_hint is content routing only
  consents[]                                  // versioned, timestamped
  data_class: K1
}

Position {                                     // a filled cell in the role grid
  id, member_id
  role: "growth" | "income" | "stabilisation" | "protection"
  capital_type: "human" | "financial"
  label, description
  magnitude                                   // annualised amount OR share of total; unit explicit
  magnitude_unit: "chf_per_year" | "share_of_total"
  // correlation tags — used to detect positions that are really one position
  tags: { client_type, skill, reputation_basis, sector, time_basis }
  started_on, active
  data_class: K2
}

Goal {                                         // container. reporting layer only, see R-030
  id, member_id, name
  target_amount, target_date
  safety, liquidity_need, volatility_tolerance // the five parameters
  funded_by_position_ids[]                     // nullable — a goal may be unfunded
  data_class: K2
}

VaultItem {
  id, member_id, kind                          // policy, statement, contract, note, ...
  title, source: "upload" | "forward" | "import" | "capture" | "manual"
  stored_at, content_hash, version, supersedes_id
  expiry_date                                  // drives action items — see R-060
  extracted_fields{}                           // nullable, provenance-tagged
  data_class: K3
}

Decision {                                     // the andersCH-owned Decision Record
  id, member_id, created_at, author            // member or curator
  question, options_considered[], choice, reasoning
  linked_vault_item_ids[], linked_position_ids[], linked_goal_ids[]
  curator_session_id                           // nullable
  immutable: true                              // append-only; corrections are new records
  data_class: K2
}

ActionItem {
  id, member_id, trigger_kind, due_date, status
  prepared_options[]                           // min length 2 — see C-06
  // each option: { label, consequence, cost_or_benefit, assumption_set_id }
  source_vault_item_id                         // nullable
  data_class: K2
}

AssumptionSet {                                // see C-02
  id, version, effective_from, published_by
  rates{}, horizons{}, inflation, notes
  data_class: K0
}

// knowledge and community
LearningUnit {
  id, title, body_ref, prerequisites[]
  capability_ids[]                             // what completing it evidences
  ip_owner                                     // see C-03 and section 9
}

Capability {
  id, statement                                // testable, e.g. "can explain what a
                                               // Freizügigkeitskonto in cash costs per year"
  rung                                         // see D-01 — DO NOT invent the scheme
}

CapabilityAssertion {
  id, member_id, capability_id
  evidence_kind, evidence_ref, assessed_by, assessed_at
  data_class: K2
}

// market place
Listing {
  id, provider_id, roles[]                     // growth | income | stabilisation | protection
  domain: "financial" | "health" | "education"
  qualification_pipeline: "capability" | "professional_registration"
  registration_refs[]                          // for the professional pipeline
  disclosures[]                                // economic relationships — mandatory, may be empty only
                                               // if explicitly asserted as none
  standing_inputs{}                            // capability evidence, community presence
  // NO paid placement field readable by ranking — see C-08
}

CuratorSession {
  id, member_id, curator_id, opened_from, opened_at, closed_at
  outcome, liability_flag, decision_ids[]
  append_only: true                            // see C-10
}
IDRequirement
R-020A Position is valid with only one row filled. The grid must render and be useful at n=1
R-021Position.tags are used to detect positions that are effectively one position. The comparison rule and its threshold are not yet decided — see D-02. Store the tags; do not ship the inference
R-030Goals never partition holdings. A single portfolio must be representable against many goals. No requirement that funded_by_position_ids be disjoint across goals
R-031A goal whose funding has a liquidity profile inconsistent with its target_date is surfaced as a statement of fact, not as a warning to be dismissed
R-040Decision records are immutable. A correction is a new record referencing the prior one
R-041Vault items are versioned with supersedes_id. Nothing is overwritten in place

05 Screens

S-01

Onboarding

Purpose
Establish enough to render the role grid with at least one position and one goal
Reuse
An onboarding questionnaire already exists in the estate with a versioned schema. Survey it, report its question count and schema version, and propose a mapping to Position and Goal rather than writing a new one
Requirements
  • R-100 Age floor 25 enforced server-side, not only in the form
  • R-101 Must be resumable. Partial state persists per question, not per session
  • R-102 Ends by writing one Position (employment, human capital, income role) and the member's first Goal if stated
  • R-103 Consent is captured as versioned records, not a checkbox boolean
Accept
A member who abandons at question n and returns resumes at n. Registration with a stated age of 24 is refused by the API even if the client is bypassed
S-02

Role grid — default landing

Purpose
Four roles across two kinds of capital. The structure the product is organised around
Layout
Four rows (Growth, Income, Stabilisation, Protection) × two columns (human, financial). Eight cells, each empty or holding one or more positions
Requirements
  • R-110 Renders meaningfully with a single position filled. Empty cells state what would go there, not "no data"
  • R-111 Each role shows its definition on demand. Definitions are content records, not hardcoded strings — see D-03
  • R-112 Adding a position is reachable from any empty cell in one action
  • R-113 No completion meter, no "3 of 8 filled", no progress ring
  • R-114 Where a figure exists in both kinds of capital, both are shown together
Accept
A member with one position sees a screen that tells them something. No element implies eight positions is the goal
S-03

Position detail and add position

Requirements
  • R-120 Captures role, capital type, label, magnitude with an explicit unit, and the five correlation tags
  • R-121 Human-capital positions capture a time basis, because hours are the binding constraint. Financial positions do not
  • R-122 A position may be marked inactive. Inactive positions remain in history and in decisions
  • R-123 Creating or editing a position writes a Decision in the same transaction — C-09
S-04

Containers

Purpose
What each franc is for. A reporting and decision layer over whatever is actually held
Requirements
  • R-130 Goals may reference overlapping funding. The UI must not imply separate accounts
  • R-131 Each goal shows the five parameters and whether its funding matches its date
  • R-132 Courage money is a first-class goal template, not a footnote
  • R-133 Any projection is an illustration under C-02 and displays its assumption set
S-05

Stage map — the climb

Purpose
Content navigation across five stages: 25 career start, 30 family and home, 35 own business, 45 a large asset, 50 optimising
Requirements
  • R-140 Stages describe a situation. No grading, no locking, no "you are here" score
  • R-141 A member may open any stage regardless of age
  • R-142 No stage after 50. Drawdown content is out of scope — NG-02
  • R-143 Mountain language appears in marketing surfaces only, never in the authenticated product
S-06

Vault

Requirements
  • R-150 Four intake paths, behind one interface: manual upload, forwarding address, import, camera capture. Build the interface now; the first automated path is D-04
  • R-151 Extracted fields carry provenance and a confidence indication. Extraction never overwrites a member-entered value
  • R-152 Expiry dates are first-class and are the primary source of action items
  • R-153 Member-authored notes, learning and family arrangements are vault items of equal standing to documents
  • R-154 Full export of everything the member owns, in a documented format, without asking anyone
S-07

Decisions

Purpose
The record of what was decided and why. This is an andersCH-owned component and the thing that survives a change of adviser
Requirements
  • R-160 Chronological, filterable by linked position, goal or vault item
  • R-161 Shows author and whether a curator was involved
  • R-162 Append-only. The UI offers "record a correction", never "edit"
S-08

The Know — MiniMind panel

Purpose
Answers grounded in the member's own vault, the learning material, and the always-open route to a human
Requirements
  • R-170 Persistent across all authenticated screens. Carries a Curator button at all times
  • R-171 Answers cite which vault items or learning units they drew on
  • R-172 A question that would require a personalised recommendation returns an explanation of the boundary and a Curator handoff — never a hedged recommendation. C-01
  • R-173 The Curator button opens a CuratorSession recording the screen it was opened from
  • R-174 Action items are listed here, each expandable to its prepared options and their consequences
  • R-175 No unsolicited proactive messages. An item appears in the list; it does not interrupt
Accept
Asked "should I buy fund X with my 10,000", the system explains the boundary and offers a curator. It does not answer, and it does not produce a suggested breakdown
S-09

Life event modules

Purpose
Seven modules: separation, job loss, illness and incapacity, death of a partner, inheritance, caring for parents, move abroad or return
Requirements
  • R-180 Each module is a content record with the same shape: what to do first, what not to sign, which vault items to retrieve, which curator to call
  • R-181 A module pulls the relevant vault items automatically rather than asking the member to find them
  • R-182 Reachable from The Know without navigating a menu
  • R-183 Module content is authored, not generated. Ship the framework with the modules empty rather than filling them with generated text
S-10

Learning path and capability review

Requirements
  • R-190 Units have prerequisites and evidence one or more capabilities
  • R-191 Progression is expressed as capability statements the member can read. No level numbers, no points — C-07
  • R-192 The rung scheme and the assessment method are not decided — D-01. Build the data model and leave the scheme configurable
  • R-193 Three exits are named in the content: run your own affairs, offer a service, start a venture. Only the second and third touch the Market Place
  • R-194 No claim, anywhere, of federal or accredited status — NG-04
S-11

Market Place — browse and listing

Requirements
  • R-200 Indexed by the four roles, not by profession. A provider may appear under more than one role
  • R-201 A member's own role grid pre-filters the view, and the filter is visible and removable
  • R-202 Every listing displays its disclosures. A listing with no disclosure record cannot be published
  • R-203 Ranking inputs are role match, capability evidence and community presence. No commercial input — C-08
  • R-204 Two qualification pipelines: capability-assessed for financial supply, professional-registration for health and education. A listing declares which, and they are not interchangeable
  • R-205 Member offers and searches sit alongside provider listings: co-investment, succession, property, skills and services
S-12

Curator Workbench

Purpose
The curator-side surface. An andersCH-owned component
Requirements
  • R-210 Curator sees the member's vault, positions, goals and decisions only after the member grants access, scoped and time-limited
  • R-211 Every session is recorded with entry point and outcome — C-10
  • R-212 A recommendation made by a curator writes a Decision attributed to that curator
  • R-213 Access grants are revocable by the member at any time, with immediate effect
S-13

Community

Requirements
  • R-220 Lectures, café evenings and meet-ups as scheduled items with attendance
  • R-221 Attendance is an input to community presence for Market Place standing — recorded, and not shown to the member as a score
  • R-222 The word "events" in the interface means life events. Gatherings are named as lectures, evenings or meet-ups
S-14

Settings, consent and data

Requirements
  • R-230 Consent history visible and withdrawable
  • R-231 Export and deletion self-service, both producing a Decision record of the request
  • R-232 A plain statement of which data class each stored category falls into

Enforcement point

/api/know/ask is where C-01 lives. The boundary check runs server-side on the response before serialisation. It must not be a prompt instruction alone — a model that ignores its instructions has to be caught by code.

07 Engine integration

The estate contains a set of analytical engines. Several run out of process because their dependencies are mutually incompatible, each with its own environment. Preserve that pattern; do not attempt to unify the dependency tree.

# pattern: one subprocess per engine, its own venv, JSON over stdio
engines/
  <engine_name>/
    .venv/                  # isolated, never shared
    run.py                  # reads JSON on stdin, writes JSON on stdout
    manifest.json           # name, version, inputs, outputs, timeout, owner

# backend call site
result = call_engine(
    name="life_balance_sheet",
    payload={...},
    timeout_s=<from manifest>,
)
IDRequirement
R-300Every engine declares a manifest.json with its inputs, outputs, timeout and IP owner. An engine without a manifest is not callable
R-301Engine calls are never made on a request thread if the manifest timeout exceeds two seconds. Queue and poll
R-302Engine failure degrades the screen, never the session. A failed engine renders as "not available", not as a zero
R-303Engine inputs and outputs are logged with the member reference removed, for reproducibility without exposure
R-304No engine, weight file or model artefact is served to the browser under any circumstance — C-03
R-305Report the engine inventory found in the estate, with each one's declared owner, before wiring any of them

08 Design principles as code rules

Each principle forbids something specific. The right-hand column is the testable form.

#PrincipleForbidden in code
1Answer the question, then show the bigger leverA path that returns only a redirect to onboarding when a member asks a direct question
2The first session produces one true, specific statement about the member's own situationAn onboarding completion screen that only echoes submitted values
3Design for one position, not fourAny component that throws, renders empty, or shows a placeholder skeleton when only one position exists
4An interruption arrives with the decision prepared, or not at allPush, email or in-app message without a prepared_options payload. Badge counts on navigation
5The daily loop is perspective; the deep work is episodicStreak counters, daily-goal state, "you haven't visited in n days" copy anywhere in the planner
6Help is one tap; standing is earnedCurator access conditioned on learning progress. Any commercial input to listing order
7One portfolio, many meaningsA uniqueness constraint forcing each holding into exactly one goal
8Educate and illustrate by default; recommend only through a licensed humanAny endpoint returning ranked instruments without an open curator session
9State every figure in both kinds of capital where both applyA summary component that accepts only financial inputs
10Plain language in the product; metaphor in the marketingMountain, hut, tour, summit or climb vocabulary in authenticated UI strings

On underspecification generally

This document is deliberately silent where a decision has not been taken. Silence is not permission to choose. If a screen cannot be built without an answer, say which answer is needed and stop; a wrong policy baked into a schema costs more to remove than the delay costs to absorb.
