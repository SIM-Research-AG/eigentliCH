# Part 2 — The constraints

## What the owner has ruled

Regulatory compliance is not a constraint on this build. The report is valid advice only
once a curator has looked at it, so the human is the gate and the code does not need to
decide whether a sentence is advice.

This is a sound trade and A76 is the evidence for it: 255 patterns, four rounds since, each
finding a class nobody had listed, and a written conclusion that the approach does not
converge. What is being deleted is the most expensive thing in the build to maintain.

**It is a swap, not a deletion, and the swap has to land in the same pass.** Today nothing
stops output reaching a member unreviewed: phase 5's curator screen is a sign-in and a
worklist, with no screen for a session's notes and none for a recommendation, and A156
dropped the grant requirement for the dashboard. Delete C-01 without the release gate and
the sentence "a curator looks at it" describes an intention rather than a control.

**T2.1 — `OWNER RULING REQUIRED`: the release gate.**
Proposed, for Nicolas to accept, amend or refuse:

> **C-12 — No plan output reaches a member until a named curator has released it.** Every
> report, finding and allocation carries a release record: curator id, timestamp, and the
> assumption set it was computed against. Unreleased output is visible to the curator and
> to nobody else.

One chokepoint, provable from the audit trail C-10 already keeps. If the answer is instead
that the curator is advisory and reports reach members directly, say so and record it,
because then nothing in the system holds the claim that a human read it.

**Do not start Part 2 until this is answered.** Everything below assumes an answer exists.
