# Mandate register

Which mandate files in this directory are current, and which are not. Rewritten 2 August 2026, when the
legacy institutional mandates were deleted and the demo set was aligned to the five book lives.

## Deleted, 2 August 2026 — by explicit instruction, overriding M1

`DECISIONS.md` M1 rule 2 says a superseded file gets a declared current version, not a deletion. The user
overrode that for this one case, in these words: *"Get rid of all the legacy institutional mandates (delete in
this case)."* Recorded here because a rule that is overridden silently stops being a rule.

Twelve mandate files and eight generated outputs were removed. They were inherited from the legacy optimiser,
described institutional mandates rather than households, and nothing in the master model's per-user path read
them — the household flow derives its mandate rather than loading one.

```
Beisheim_Beisheim_Mandate.yaml      G7nesis_G7nesis_Mandate.yaml    G7Nesis_LS.yaml
G7Nesis_MA.yaml                     G7Nesis_TF.yaml                 PK_Post_PKPost_Mandate.yaml
Silverhorn_Belvedere_SI.yaml        SIM_Dynasty_Office.yaml         SIM_Dynasty_Test.yaml
SIM_Global.yaml                     SIM_Gold_Equity.yaml            SIM_Swiss_Office.yaml

output/  Beisheim_*.csv .json _brief.md _challenge.json _challenge_brief.md
         PK_Post_*.csv .json _brief.md
```

**The deletion is reversible, which an earlier draft of this note got wrong.** These files were never
hand-written: `tools/seed_mandates.py` generated them, read-only, from the legacy Controller workbook at
`SIM_Tech/Master_Controller/Controller_Test.xlsx` — still present, 66 KB, last modified 3 June 2024. So
although no copy of the YAML survives and there is no version control, the source does:

```
python -m tools.seed_mandates          # regenerates all twelve from the workbook
```

Worth knowing before anyone treats their absence as final. The generated outputs under `output/` would need a
re-run of the pipeline rather than the seeder.

`Beisheim_Beisheim_Mandate.yaml` was load-bearing: `pcp/tests/test_end_to_end.py` named it in its `MANDATE`
constant. That test now runs against a book-life mandate instead — see below.

## Current

### The five book lives

The five editable presets the Life Balance Sheet app ships — `Young professional`, `Independence by fifty`,
`Near-retiree`, `Entrepreneur`, `Tail shock` — are the same people the master model demonstrates on. Before
this, the app had five presets and the master model had three unrelated households, so a reader moving between
the two surfaces met two different casts.

| File | Life | Position | Goal |
|---|---|---|---|
| `life_young_professional.yaml` | Young professional, 28 | 40k liquid | FI, 12y, 65% confidence |
| `life_independence_by_fifty.yaml` | Independence by fifty, 40 | 1.6m / 1.1m / 300k debt | FI, 10y, 85% |
| `life_near_retiree.yaml` | Near-retiree, 60 | 1.6m / 1.4m / 100k debt | retirement, 5y, 90% |
| `life_entrepreneur.yaml` | Entrepreneur, 46 | 300k / 2.5m / 600k debt | FI, 8y, 80% |
| `life_tail_shock.yaml` | Tail shock, 44 | 900k / 700k / 250k debt | FI, 6y, 85% |

These are **hand-authored and stable**, unlike the derived files below. The Optimiser's own end-to-end test
runs against one of them, and a test that depended on a regenerated artefact would fail whenever the Regime
moved.

### Derived from the roster — regenerated, never edited

Written by the Life Balance Sheet each time the per-user path runs with `derive_mandate=True`, and
materialised here in the Optimiser's own format. Transport, not source: the derivation happens in the engine
(`DECISIONS.md` M4). Editing one has no effect that survives the next run.

`derived_hh-0001.yaml`, `derived_hh-0002.yaml`, `derived_hh-0003.yaml`

## Cleared, 2 August 2026

Ten derived mandates for households that no longer exist. Deleted rather than kept, on the same instruction
that removed the legacy set: these are **generated transport files**, regenerated by the Life Balance Sheet
whenever the per-user path runs, so nothing is lost that a run would not rewrite. Keeping mandates for retired
households in a directory the Optimiser enumerates only makes it harder to see which five are real.

- `derived_hh-0003` — from the three-household roster the five book lives replaced (M47).
- `derived_hh-test`, `derived_hh-probe`, `derived_hh-journey` — the suite's, the validation probes' and the
  journey's own households, retired onto roster ids on 1 August.
- `derived_hh-surplus-A` to `-D` — four candidate preservation households from a throwaway script written
  while choosing the old roster's third client.

### `derived_hh-0001` and `derived_hh-0002` come back, and that is correct

They were deleted with the rest and reappeared within the minute. **They are not stale demo artefacts: they
are test output.** `tests/conftest.py`, `test_control_plane.py` and `test_curator.py` use `hh-0001` as their
household, `test_client.py` and `test_per_user_path.py` use `hh-0002`, and those tests run the per-user path
with `derive_mandate=True` — which materialises a mandate here as a side effect of asserting that the
derivation works.

So expect exactly two of these after any `make test`, and do not read them as roster state. Their figures will
not match anything on a board: the tests use their own positions, so the regenerated `hh-0001` asks for
15.6150% where the retired roster household asked for 14.1525%.

Two things follow, neither urgent. **The suite writes into a directory the Optimiser enumerates**, which is why
`pcp.cli mandates` lists households that no demo has. And **the fixture ids are now confusable**: `hh-0001` and
`hh-0002` were roster ids until 2 August and are now only test fixtures, so a reader meeting one has no way to
tell which it is. Renaming them to something obviously a fixture would fix both, and would partly reverse the
1 August decision to put fixtures on roster ids — that decision was right when roster ids were the only real
ones, and is worth revisiting now that the roster has moved.

**Not cleared, deliberately: the event streams and the review queue.** `data/fdt/` still holds `hh-0001`,
`hh-0002` and `hh-0003`, and the Curator queue still holds twelve submissions for them. Those are not
generated outputs — the FDT store is append-only, hash-chained and consent-gated, and the queue is the audit
record of what was submitted and decided. Deleting from either would break a chain whose whole purpose is that
it cannot be edited after the fact. Whether a retired demo household should be purged from an audit store is a
question about retention policy, not housekeeping, and it belongs with the consent and erasure work rather
than with a tidy-up.
