# pcp: decisions index

Every choice the sources left open or disagreed on, and every intentional divergence from the prior art, with
the reason. Sources, ranked as the Engine Build Instruction ranks them: the Engine Building Guide, the Engine 07
page, the System Build Manual (sections 14, 15, 20 to 22), the eigentliCH PCP draft
(`Projects/eigentliCH/engines/PCP`, its spec `CLAUDE_CODE_portfolio_creation_program.md` and decisions D0 to D29)
and the MATLAB predecessor (`SIM_Tech/Master_Controller/Functions/PCP`).

| Id | Decision | Reason |
|---|---|---|
| PCP-01 | The engine lives in its own family folder, `Projects/Engines/Optimizer/engines/pcp`, with the family's own `.venv` (Python 3.12, scipy 1.18). Anatomy, settings, store, service and API follow `aggregation`. | Engine Build Instruction section 3: a new family gets `<Family>/engines/<module>` and one shared environment. |
| PCP-02 | `psycopg` is outside the allowlist and admitted. | The Guide mandates PostgreSQL; a driver is unavoidable (as honi D-05, aggregation AGG-02). |
| PCP-03 | The objective is the draft's and MATLAB's: `sum_i (sum_j max(C_i - M_i x_j BB_ji, 0))^2`, the shortfall summed over instruments before squaring, with the exact gradient (the inactive sub-gradient at a kink). `profile_scale` (calibration, 1.0) multiplies the profiles inside it. | Owner's ruling, 28.09.2026, over the Manual's portfolio form `sum_s pi_s max(0, r*_s - w'r_s)^2`. Consequence, reported on every Allocation (`objective_floor`, `weight_leverage`, a note below 5%): a zero-weight instrument still adds its full target to every state, so on fmre's 54 instruments the weights control about 0.6% of the objective and the constraints settle the allocation (draft D28). MATLAB behaved differently only because its profiles were in percent against a decimal curve, not because its regime rows summed to 100 as draft D29 guessed; `profile_scale` 100 would bring that behaviour back as a new calibration. |
| PCP-04 | The client's regime distribution is blended in pcp: the mandate carries `regime_weights` (economy code to weight, summing to one) or names one of aggregation's markets as a preset for its published weights. The month is the request's `date`, else the latest month in which every weighted economy is assessed. A weighted economy that is not assessed in that month is refused, never dropped or re-weighted. | Owner's ruling, 28.09.2026 ("aggregated individually per client"). The Regime's `regime_id` is stamped unchanged; the weights and month are in the Allocation's provenance and in the idempotency key. |
| PCP-05 | Regime state s weights profile state s (identity), both 1 = crisis to 25 = boom. | Owner's ruling, 28.09.2026. fmre notes that its states are not the Regime's (its own quantile map bridges the old andersCH signal); the draft and MATLAB used the identity. |
| PCP-06 | Instrument classification: fmre's register is the authority for every attribute it carries (role, asset class, currency, capital type, liquidity, region). The calibration's classification table supplies what the register does not carry (economic phase, home scenario, ESG) and fills liquidity and region where the register holds none (10 instruments each). The table is the prototype's published 54-instrument universe, the file fmre's register was imported from. | The 75-row block and the portfolio map need all nine attributes; fmre has six. Every ESG score in that universe is 1.0, so the ESG row cannot discriminate yet (a warning on every run). Open point for fmre: publish phase, home scenario and ESG itself. |
| PCP-07 | Profile values of weak method (`borrowed`, `seed`) are accepted and reported: each instrument's weakest method, and the share of the weight on weak profiles. Not penalised, not a constraint. | The engine page left it open; none of fmre's 54 instrument profiles is data-driven today, so a penalty or a constraint would leave nothing to allocate. Revisit when fmre publishes data-driven instrument profiles. |
| PCP-08 | The budget is read from the raw solution, before renormalising. Calibration 1.0.0 keeps the draft's `round(sum, 1) == 1` (accepts 0.95 to 1.05); 1.1.0, the active one, requires `abs(sum - 1) <= 1e-6`. | Manual section 15.2: "the single most likely silent failure". 1.0.0 exists to reproduce the draft. |
| PCP-09 | fmre serves its current ReturnSet only and does not version its register rows: the request must name the `return_set_id` fmre serves (else refused), and the register mirror reads named fields, reported as `fmre-register (unversioned)`. | fmre has no `/artefacts/{id}` and no by-id read of a past set. Its `return_set_id` also depends on the include flags (instruments, blocks): pcp reads and names the set with instruments, without blocks and stamped with the requested `regime_id`, which also enters the id. |
| PCP-10 | Row layout: dimension by dimension, each bucket a floor row then its ceiling row; ESG row 57, floor only; starts 1, 21, 35, 43, 49, 57, 58, 66; 75 rows; checked on every build (`verify_layout`). | Manual section 15.2 and Step 25. The draft and MATLAB grouped all ceilings, then all floors; the dimension starts and row 57 agree, and the solution is the same to 3e-14 either way (measured on golden layer A). |
| PCP-11 | The `regime_id` rule is strict: a ReturnSet whose `regime_id` is not the requested one is refused, and so is one that carries none. | Owner's ruling, 28.09.2026 (Guide section 4). pcp asks fmre for the set stamped against the requested Regime (`/v1/return-set?regime_id=`, confirmed by fmre with aggregation) and still checks the stamp it receives; an unstamped set is refused. Manual 15.7 test 3 compares with the `DerivedMandate`'s id; here with the requested Regime's (the engine page's contracts win, Build Instruction section 1). |
| PCP-12 | Contracts: the engine page's `Mandate` in and `Allocation` out (shared with mvopt), not the Manual's `DerivedMandate` and `Recommendation`. The Allocation carries raw and renormalised weights separately, the active constraint set and `release_state = unreleased`, which is the only value it can hold: constructing a released one raises (Manual 15.7 test 6). Bound sources follow Manual section 14.2 (currency, liquidity, role derived; asset class, capital type, phase, region policy); a mislabelled source is refused in both directions (test 5). ESG, not among the seven dimensions, takes no source. | Build Instruction section 1: where the Manual and the engine page disagree about what the engine publishes, the engine page wins; the Manual's release boundary is kept. |
| PCP-13 | The mandate declares `curve_unit`, which must equal the profiles' unit (fmre: `annualised_log_return`); the horizon must be one year. | The MATLAB compared a decimal curve with percent profiles (draft D2). The profiles are annual; compounding to another horizon is not implemented, so a longer horizon is refused rather than approximated. |
| PCP-14 | Vocabularies are the draft's and the register's (currency CHF, USD, EUR, RMB, GBP, JPY, HKD, AUD, INR, Others; region Switzerland, Europe, East Asia, South Asia, North America, South Pacific, Others; capital type Financial, Real, Others; liquidity Daily, Quarterly, Yearly, Decade; asset class Cash, Fixed Income, Equity, Real Assets, Alternative), not the Manual's. Currency, region and capital type fold unknown values into Others; the other dimensions refuse them. | The data is in these vocabularies; the Manual's (CNY, BRL, US, EU, ...) has no mapping from it. The counts per dimension agree, so the row layout is the Manual's. |
| PCP-15 | Nothing is published from an unconverged solve or from raw weights that miss the budget; a structurally infeasible mandate is refused before solving. `/validate` reports the same checks without solving. | Manual section 22 and the engine page ("infeasible mandates fail at /validate, not in the solver"). |
| PCP-16 | Solver: SLSQP from every weight at 0.5, `trust-constr` as the fallback, fast ftol 1e-3 / 300 iterations, exact ftol 1e-8 / 3000. No multi-start. | The draft (D20); Manual section 15.2 ("a deterministic solve from a fixed starting point"). The start point violates the budget; SLSQP projects in its first iterations. |
| PCP-17 | Golden: layer A, the draft's frozen runs (7 mandates), reproduced to 1e-9 on weights and 1e-12 relative on the objective (measured 2e-14 and 4e-16 with scipy 1.18 against the draft's 1.14). Layer C, this build's production cases on frozen live inputs, a regression reference. Layer B, the MATLAB Review workbooks, is not built: reproducing them needs their full bound blocks and classifications, and the legacy solve was not converged (objective differences of up to 4% measured on budget and position bounds alone). | Engine Building Guide section 6.1. MATLAB is not installed (draft D0). |
| PCP-18 | The mandate's `currency` is the reporting and return currency, one of `CHF`, `EUR`, `USD` (CHF by default). pcp asks fmre for the ReturnSet measured in it (`/v1/return-set?regime_id=...&include_instruments=true&include_blocks=false&currency=...`), refuses a set in another currency or in none, and states it on the Allocation (`currency`, `provenance.currency`, `provenance.upstream["fmre:currency"]`) and on the ValidationReport. The target curve is in the mandate's currency by definition. The currency enters the idempotency key three ways: the mandate, the `return_set_id` (fmre puts the currency into it) and explicitly. It is not an exposure bound: the `currency` dimension of the 75-row block (CHF, USD, EUR, RMB, ...) is unchanged. Contracts keep their versions: `pcp-mandate@1.0.0` is tightened from any three-letter code to the three, with the default unchanged, so every mandate the cockpit, lbs and the consumer app write today (CHF) still validates and keeps its `mandate_id`; the Allocation and the ValidationReport gain an optional `currency` (`None` only on Allocations published before this decision). The engine becomes `pcp@1.1.0`, which also retires every cached run made on a source-currency set. | Owner, 29.09.2026 ("currency selection should also be available"); review decision D-01: every return figure in CHF, EUR or USD, converted at the point of use, profiles stored nominal in the source currency. A version bump would break the readers that pin the versions exactly (`report` pins `pcp-allocation@1.0.0`; the cockpit and lbs pin `pcp-mandate@1.0.0`) for a change none of them needs to act on. |
| PCP-19 | The currency check is strict, like the `regime_id` rule (PCP-11): the set must state the mandate's currency. fmre has no structured currency field on the ReturnSet yet; it names the currency only in the note it writes on every converted set (`... in currency=CHF; not the stored default.`). pcp reads `provenance.currency` when fmre publishes it, and the note until then; a field and a note that disagree, notes naming two currencies, `currency=source`, or nothing at all are refused. Open point for fmre: a `provenance.currency` field (`CHF`, `EUR`, `USD`, or null for the source-currency default). | fmre accepts `currency` together with `regime_id` and gives each currency its own `return_set_id` (checked live, 29.09.2026: `RS-dced0b32e07034f9` CHF, `RS-9f2eab022c08c81a` EUR, stamped against `RGM-e2658e8e9bbbc81e`), but its `Provenance` forbids extra fields and has none for the currency. The note is fmre's own statement, not an assumption; the field replaces it without a change here. |
| PCP-20 | Golden: the frozen inputs are read as the CHF case. Layer A (the draft's own profiles and curves, solved by the pure engine) does not involve the ReturnSet and is unaffected. Layer C's frozen ReturnSet is fmre's source-currency default of 28.09.2026 (CHF for the andersCH series, USD for public proxies); the test double serves it as the currency the request names, and the golden cases and the tests read it as CHF, so layer C is unchanged. `dev/freeze_inputs.py` now freezes the CHF set; a refreeze moves layer C and must be followed by `dev/build_golden_production.py`. A live run no longer reproduces layer C: fmre's CHF set converts the USD proxies, and fmre's register has moved since the freeze (its stamped default is now `RS-101354ae344db5b3`); live `balanced_global` at 2024-12-31 in CHF gives objective 26.864 against layer C's 28.985. | Keeps both layers reproducing without rewriting frozen evidence; the mapping is stated rather than implied. |
| PCP-21 | Feasibility and convergence, engine-level, no new calibration. (a) `/validate` and every run refuse, before any solve, a bucket floor above what the bucket's instruments can hold under their per-instrument ceilings, a bucket ceiling below its fixed allocations, and a block whose rows conflict across dimensions, found by a phase-1 linear programme (HiGHS through `scipy.optimize.linprog`): the elastic programme minimises the total violation of the 75 rows with the budget and the per-instrument bounds kept hard, and the refusal names one smallest relaxation (row, bucket, bound, shortfall) and the other rows held at their bounds there. (b) When the calibrated solve (SLSQP from 0.5, then `trust-constr`, PCP-16) does not settle, meaning unconverged, raw weights off the calibration's budget check, or a row, the budget or a bound breached by more than 1e-6, the engine restarts from the phase-1 point (feasible, with the largest common margin on every row that bounds anything) with the exact settings, on the rows the budget and the bounds do not already imply, SLSQP first, then `trust-constr`, and keeps the first acceptable solution; the Allocation's notes say so. (c) A solve that still fails on a feasible block is reported as the solver's failure, with every attempt named. The engine becomes `pcp@1.2.0`; the calibrations and the contracts are unchanged. | Found building the 20 use cases (29.09.2026): all 18 failed runs in pcp's store (11 distinct mandates, all started from cockpit presets: 10 runs Income focus, 4 Growth global in CHF, 2 in USD, 1 Swiss home bias, 1 Balanced CHF) were infeasible as stated, not unconverged: one Gain instrument capped at 0.15 under a derived Gain floor of 0.171; three CHF instruments (0.45) under a CHF floor of 0.5; an equity floor of 0.55 or 0.30 above a Gain ceiling of 0.517 or 0.293 when every equity is a Gain instrument; a Gain ceiling of 0.293 against a Swiss floor of 0.6, a Protection floor, a real-capital floor and an equity floor together. The per-dimension checks passed them and SLSQP reported "Inequality constraints incompatible" or "Positive directional derivative". Separately, on feasible but tight blocks (the same mandates relaxed to a margin of 1e-3 or 1e-4) the calibrated fast solve fell to `trust-constr`, whose loose tolerance left the raw weights at 1.0006, off the 1e-6 budget; and SLSQP's subproblem degenerates on the about 58 of 75 rows that are implied (floors at zero, ceilings at one, empty buckets), which is why it reported incompatible constraints on feasible blocks: without them it converges from 0.5 and from the phase-1 point. The start point 0.5 itself is not the cause (the draft's projection works whenever the block is feasible and non-degenerate). Engine-level rather than a calibration because golden layer A must stay bit-for-bit under 1.0.0: the rescue engages only when the calibrated solve has not settled, which never happens on layer A (tested) or layer C, so every weight the calibrated path settles is reproduced unchanged (the Allocation's `engine_version`, and so its id, moves to 1.2.0). A new calibration field would have changed the seeds' content hash. |
| PCP-22 | The nominal and real view (owner, 29.09.2026; `review/REAL_VIEW_INTERFACES.md`). The Mandate gains an optional `basis`, `nominal` (the default) or `real`: the basis of its `target_curve`, and so of every return figure in the Allocation. pcp asks fmre for the ReturnSet on it (`&basis=real`; a nominal request sends no `basis=`, the query it sent before, which fmre serves byte for byte as its explicit `basis=nominal`), and refuses, before any solve, a set whose `provenance.basis` differs, strictly like the currency and the `regime_id`; a set without `provenance.basis` counts as nominal. fmre's `422 {"status": "not_computable"}` (decision 5: no currency inside the band) is a refusal with fmre's reason, not an outage; so is a real set whose `deflator.labels` name a state `not_computable`. The Allocation states `basis` (top level and `provenance.basis`); a real one also carries `fmre:basis`, `fmre:deflator` (currency, index, method, scenario) and `fmre:hard_currency_fallback` in `provenance.upstream`, and a warning with the per-state label counts and any hard-currency fallback, reported as fmre publishes them and never recomputed. The basis enters the idempotency key through the mandate, through fmre's `return_set_id` and explicitly when real. **A nominal mandate is byte for byte what it was**: `Mandate`, `Allocation` and `Provenance` serialise `basis` only when it is `real`, and the ReturnSet mirror leaves out an unstated `basis` and `deflator`, so a mandate without the field, or with `basis: nominal`, keeps its `mandate_id`, its idempotency key and its Allocation's `artefact_id` (pinned in `tests/test_basis.py`), and a body without `basis` reads back as nominal. No contract version and no engine version moves (`pcp-mandate@1.0.0`, `pcp-allocation@1.0.0`, `pcp@1.2.0`); the ValidationReport states `basis` always. A real set on a hard-currency fallback (decision 5) is governed by PCP-23. | The spec binds the fields and the refusal. Leaving the default out of the JSON is the only way to state a new field and keep every content-addressed id of a nominal mandate, which the consumers (cockpit, lbs, report) cache and pin; stating `basis: nominal` explicitly would have moved every `artefact_id` and idempotency key for no change in any figure. A version bump would have broken the readers that pin the versions exactly, as under PCP-18. |
| PCP-23 | The hard-currency fallback is accepted, clearly marked (owner, 29.09.2026). When a real mandate's currency leaves fmre's -20 % to +100 % inflation band in a state, fmre measures the real set in CHF, then USD (its decision 5, `engines/fund_map/inflation.py::hard_currency`): `provenance.currency` is the hard currency, the notes name it, and `provenance.deflator.hard_currency_fallback` is `{from, to, states, reason}`. pcp's currency check accepts a set whose currency differs from the mandate's **only** when the mandate and the set are real, the fallback's `from` is the mandate's currency, its `to` is the served currency, and the deflator's `currency` (when stated) is the served one too. Every other mismatch stays refused, with the reason: another currency without a fallback, a fallback on a nominal mandate, a fallback from another currency (also when the set is in the mandate's own currency), a fallback to a currency other than the served one, an incomplete fallback. The Allocation states it: `currency` and `provenance.currency` are the hard currency (the currency every return figure is in, as PCP-18 defines `currency`), `provenance.hard_currency_fallback` is fmre's `{from, to, states, reason}` unchanged (`from` is the mandate's currency), `provenance.upstream` keeps `fmre:currency` and `fmre:hard_currency_fallback`, and `coverage.warnings` opens with the plain statement "real, measured in CHF because EUR inflation left the computable band (fmre's -20 % to +100 %) in states [...]", which also stands in the ValidationReport's `notes`, beside its `hard_currency_fallback`. The fallback enters the idempotency key through the `return_set_id`: fmre derives the id from the asked currency, the served one and the fallback, so the request for a fallback set names an id of its own; pcp cannot add it explicitly, because the key is looked up before fmre is asked. It also enters the `artefact_id` through the Allocation's content. `hard_currency_fallback` is left out of the JSON when there is none, so every other Allocation and ValidationReport keeps its bytes and ids; no contract or engine version moves. | The alternative, refusing, would leave an EUR client with no real view whenever EUR inflation leaves the band although fmre has a computable one in CHF; accepting it silently would show CHF figures as EUR. Stating the hard currency in `currency` keeps every reader that knows only `currency` correct about the figures it shows; the fallback's `from` keeps the mandate's currency on the artefact. The target curve stays the mandate's real curve: real returns in two hard currencies are close but not identical, which the warning says. |
| PCP-24 | **Health probes stay out of the access log** (03.10.2026, `deploy/ENGINE_CHANGES.md` item 10). `access_log.py` puts a filter on uvicorn's `uvicorn.access` logger, installed at the top of `create_app` (uvicorn configures its loggers before it calls the factory). It drops a `GET /health` line that answered below 400, matched on the path without the query string; every other request is still logged, and so is a health call that answered 400 or more. No new dependency; `tests/test_access_log.py`. The engine version stays `pcp@1.2.0`: it enters every idempotency key (`Service.idempotency_key`), so a bump would give a rerun of unchanged inputs new ids for a change that alters no figure. | The container's health check calls 14 routes every 30 seconds, about 40,000 health lines a day between the lines that matter. A failing probe is the line worth reading, so it stays. |
